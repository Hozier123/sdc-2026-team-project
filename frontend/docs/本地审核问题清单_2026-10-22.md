优先级：P1 为核心业务正确性或可用性问题；P2 为编辑、恢复、加载和交付问题；P3 为边缘体验或优化项。

## A01 · P1：重复 SKU 的拣货行相互联动

**位置：** [fulfillment.tsx:958](../src/components/fulfillment.tsx#L958)、[demo.ts:1330](../src/lib/demo.ts#L1330)。

**复现步骤：**

1. 在本地演示中选择普通客户，新建两行 `Tepung 1 ctn`、`Tepung 2 ctn`。
2. 批准生成送货单，切换仓库角色，查询这张送货单。
3. 只勾选第一行。

**实际结果：** 两个复选框均变为已勾选，但页脚显示 `1 / 2 items checked locally`。

**原因与影响：** 服务允许重复 SKU 行，仓库投影也逐行保留；UI 却用 `sku_id` 同时作为 React key 和勾选状态标识。两个独立数量行共享状态，可能让尚未核对的行看起来已完成。

**建议：** 定义明确的拣货行身份。若按 SKU 汇总，应同时汇总数量并统一展示；若保留明细，应保留稳定行 ID，使用行 ID 管理勾选。不能只修改 React key 而继续用 SKU 存状态。

**复验标准：** 重复 SKU 两行可独立勾选且计数准确，或者被正确合并为一行、总量为 3 ctn。

**证据：** [仓库重复勾选截图](audit/warehouse-duplicate-selection.png)。

## A02 · P1：辅助接口故障扩大为整个工作区不可用

**位置：** [App.tsx:228](../src/App.tsx#L228)、[App.tsx:537](../src/App.tsx#L537)。

**复现步骤：**

1. 使用本机模拟 API，令 `/me`、`/ai/status`、`/orders/drafts`、`/approvals` 正常返回。
2. 仅令 `/activity` 返回 503。
3. 进入工作台，再点击 Order inbox。

**实际结果：** 所有主区都显示活动接口的错误，订单列表无法展示，尽管草稿接口已成功返回。

**原因与影响：** 三类数据共用 `Promise.all` 和一个全局 `boot.error`。任何一项失败都会阻止整个业务路由树渲染。审计展示服务的短暂故障因而影响查看订单及继续操作。

**建议：** 将身份初始化与各业务资源的加载状态拆开；活动摘要失败只在对应区域显示错误和重试。审批页失败也不应阻断独立订单详情。不能把失败的活动数据默默当成空列表。

**复验标准：** 单独注入活动或审批列表故障，其他正常的业务模块仍可访问，故障区域有明确状态和局部重试。

**证据：** [活动故障阻断订单截图](audit/activity-outage-blocks-inbox.png)。

## A03 · P2：已经离开的创建请求仍强制导航

**位置：** [orders.tsx:126](../src/components/orders.tsx#L126)、[App.tsx:570](../src/App.tsx#L570)。

**复现步骤：**

1. 新建订单，挂起解析接口响应。
2. 点击 Overview，在离开确认中选择 `Discard changes & leave`。
3. 确认已回到 `#/workspace`，再释放解析响应。

**实际结果：** 地址从工作台自动变为 `#/order/DRF_AUDIT_ASYNC`。

**原因与影响：** 组件卸载后，旧请求的回调仍调用父级 `complete` / `forceNav`。用户已经明确离开，仍被迟到响应改变当前操作位置。

**建议：** 用组件生命周期或请求代次检查丢弃过期 UI 回调；明确处理中能否离开的交互。取消前端等待不等同于取消后端创建，应保留查询结果和重复提交保护。

**复验标准：** 解析期间离开、返回、重新创建或切换连接后，旧响应不会跳转或覆盖当前表单；已创建记录仍可从列表查找。

## A04 · P2：保存中的新修改被返回快照覆盖

**位置：** [orders.tsx:340](../src/components/orders.tsx#L340)、[orders.tsx:824](../src/components/orders.tsx#L824)、[orders.tsx:698](../src/components/orders.tsx#L698)。

**复现步骤：**

1. 使用带手工匹配商品的草稿，修改数量并点击 Save changes，挂起保存响应。
2. 数量框已经禁用，但 `Remember this phrase…` 复选框仍可操作。
3. 勾选该项后释放保存响应。

**实际结果：** 请求中的 `save_to_alias_cache` 为 false/未设置；刚勾选的复选框变回未选中，页面显示 `Saved and checked`，没有提示新修改未保存。

**原因与影响：** 部分控件未遵守 `busy` 状态；随后 `useEffect([draft])` 用返回快照重置全部输入并清除 dirty。用户无法判断自己的最新操作是否被保留。缺少单位的下拉框也没有 busy 禁用，存在同类窗口。

**建议：** 保存期间统一禁用所有写入控件及重置操作；或按提交版本合并响应，保留提交后发生的修改，并继续显示未保存状态。

**复验标准：** 慢保存期间不存在可以被无声丢弃的修改；请求、可见状态及“已保存”提示一致。

## A05 · P2：空数量转换为合法的 nullable 字段

**位置：** [orders.tsx:673](../src/components/orders.tsx#L673)、[orders.tsx:393](../src/components/orders.tsx#L393)、[api.ts:74](../src/lib/api.ts#L74)。

**复现步骤：**

1. 在已连接本机模拟 API 的核对页，将某一行的数量清空。
2. 点击仍然可用的 Save changes。
3. 检查实际请求 JSON。

**实际结果：** 客户端将空输入存为 `NaN`，`JSON.stringify` 将其转换成 `confirmed_qty: null`。模拟 API 接受 nullable 字段后，界面恢复原始数量 4，并进入已保存状态。

**边界：** 真实后端如何解释 null 尚未联调；本轮已经确认的是客户端把“用户清空数量”与“没有人工覆盖数量”混为同一个请求值。演示服务直接接收 NaN 时会拒绝，因此现有演示测试不能覆盖 HTTP 模式的这一差异。

**建议：** 在调用服务前验证每一行的可见数量为范围内的有效整数；空白、NaN、零、负数、小数均应就地报错并阻止保存，不能依靠 JSON 序列化隐式转换。

**复验标准：** 清空数量后不发出保存请求，有明确字段提示；合法数量才可保存。为 HTTP 模式补充空白输入回归。

## A06 · P2：AI 状态阻塞与其无关的业务数据

**位置：** [App.tsx:210](../src/App.tsx#L210)、[api.ts:65](../src/lib/api.ts#L65)。

**复现步骤：**

1. `/me` 正常返回，挂起 `/ai/status`。
2. 检查工作区和已发出的请求。
3. 释放状态响应。

**实际结果：** 挂起期间仅出现 `/me`、`/ai/status` 请求，主区一直显示 `Loading your workspace…`；草稿、审批、活动请求在状态响应后才开始。单次请求的超时阈值是 30 秒。

**原因与影响：** 状态查询被串行 await，而且位于仓库角色分流之前。AI 状态慢会拖住查看已有订单，甚至拖住仓库查询，尽管这些功能无需等待模型状态。

**建议：** 身份验证后独立加载 AI 状态；现有订单和仓库应可先显示。状态区域保留检查中、失败和重试反馈。

**复验标准：** 挂起 AI 状态时，草稿/审批请求仍会发起，仓库仍能查询送货单；超时只影响 AI 状态区。

## A07 · P2：冲突恢复按钮隐式丢弃用户修改

**位置：** [orders.tsx:1048](../src/components/orders.tsx#L1048)、[ui.tsx:99](../src/components/ui.tsx#L99)。

**复现步骤：**

1. 将数量从 4 改为 7，保存时模拟返回 409 `STALE_VERSION`。
2. 点击错误区的 `Refresh and try again`。

**实际结果：** 数量直接从 7 变回服务端的 4，未出现确认或差异保留；按钮也没有再次尝试保存，只是刷新并清除 dirty。

**原因与影响：** 恢复逻辑直接执行 `setEdit(false)`、`setDirty(false)` 和刷新。普通导航有未保存保护，这个恢复入口却会直接丢弃同类修改。

**建议：** 明确提供“保留修改并查看最新版”或“放弃修改并刷新”；放弃应说明结果。若保留输入，需要展示与新版本的差异，由用户重新确认后保存，不能自动覆盖新版本。

**复验标准：** 冲突后修改不会在含糊的重试按钮下消失；用户明确选择保留或放弃，并能在最新版本上重新核对。

## A08 · P2：当前 ZIP 与实际审核版本不一致

**位置：** `../KiraOrder_前端交付.zip`、[main.tsx:5](../src/main.tsx#L5)、[business-ui.css](../src/business-ui.css)。

**复现步骤：** 将 ZIP 中同名文件与当前本地文件比较。

**实际结果：**

- ZIP 缺少 `src/business-ui.css`，而当前 `src/main.tsx` 已导入该文件。
- ZIP 内的 `src/App.tsx`、`src/components/ui.tsx`、`README.md` 与本地不同。
- ZIP 中生产资源为 `index-B3HnRv9D.css`、`index-D-m1RQL0.js`；本轮构建产物为 `index-CPyzxUVK.css`、`index-CLpoLS46.js`。

**影响：** 收到 ZIP 的人无法得到当前浏览器中展示和本轮审核的版本，业务页面视觉统一及状态提示更新未完整交付。

**建议：** 在修复、复验后统一重新构建并打包，记录版本或文件校验值；从解压目录单独安装、构建和演示。此次审核保持原 ZIP 不变，避免把未修复版本当成新验收包。

**复验标准：** 源码、构建和说明来自同一版本，ZIP 包含业务样式；解压后构建及主要流程通过。

## A09 · P3：不完整详情路径没有兜底页面

**位置：** [App.tsx:576](../src/App.tsx#L576)、[App.tsx:596](../src/App.tsx#L596)、[App.tsx:613](../src/App.tsx#L613)、[App.tsx:629](../src/App.tsx#L629)。

**复现步骤：** 分别访问 `#/order`、`#/approval`、`#/delivery`，不提供记录 ID。

**实际结果：** 面包屑变化，但 main 内无标题、无错误说明或返回操作。本轮连接模式下 main 文本为空。

**原因与影响：** 缺 ID 时详情组件不会渲染，但路由前缀又被视为合法，绕过了兜底页面。残缺链接或误编辑地址会造成空白区。

**建议与复验：** 对完整路由形状进行验证；缺 ID、空 ID 或非法路径应显示可恢复的错误页或跳回对应列表。三个路径均须有清晰反馈。

## A10 · P3 优化项：初始场景仍携带大块内嵌资源

**位置：** [intro-scene.html](../public/intro-scene.html)、[intro-refinement.css](../public/intro-refinement.css)。

**测量结果：** HTML 为 6,484,368 字节，内嵌 11 个字体 face；字体 base64 共 3,801,392 字符，PNG base64 共 2,249,804 字符。其中 Cinzel 与 Inter 合计约 186 万 base64 字符，而当前首页排版已主要统一为 Cormorant Garamond。

**影响与边界：** 大型内嵌文件不能让字体、背景分别复用缓存；修改介绍文案也会使整份资源重新加载。本轮未做真实移动网络计时，因此不声称具体慢多少秒，也不把它作为功能失败。

**建议：** 在保留原始参考文件的前提下，将实际使用的字体和背景拆为静态资源，清除未用字重及字体，配置缓存和压缩；再比较冷启动、热启动及低性能设备动画开销。

**复验标准：** 入口传输体积有可测下降，字体无闪烁或缺字，星空、70% 缩放及两处进入按钮正常。
