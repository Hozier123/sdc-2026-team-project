## 2. 在本地使用 fixture mock

首次安装依赖后，分别打开两个终端，在项目目录运行：

```sh
# 终端一：前端
npm run dev
```

```sh
# 终端二：固定快照接口
npm run mock:api
```

在前端侧栏点击 **Connect API**：

- API base URL：`http://127.0.0.1:4191/api/v1`。
- Session token：`fixture-clerk`、`fixture-owner` 或 `fixture-warehouse`。这是固定的合成测试标识，不是真实会话凭据。
- 连接后应看到 **FIXTURE MOCK · Synthetic responses · no real backend**。

切换场景：

```sh
npm run mock:scenario -- price
npm run mock:scenario -- candidate
npm run mock:scenario -- stock --save=stock
npm run mock:scenario -- pending
npm run mock:scenario -- pending --error=STOCK_CHANGED
```

| 场景 | 用来检查什么 |
| --- | --- |
| price | 初始价格疑点 → 保存固定 ready 快照 → 202 待审批 |
| candidate | 未选商品、候选价格与库存、选择后必须保存 |
| stock + save=stock | 保存返回 200，但仍存在缺货阻断，不能把保存成功等同可以批准 |
| pending | OWNER 读取审批快照、98.00 → 95.00 修改值、批准或带理由驳回 |
| pending + STOCK_CHANGED | 批准收到 409 时保持待批，展示刷新入口 |

切换后在已打开的订单点击 **Refresh saved order**；查看列表时可重新连接对应 fixture 身份加载快照。刷新整个浏览器会丢失内存会话并回到本地演示，届时需重新连接。

该服务只监听 127.0.0.1，浏览器跨域来源限本机 HTTP；不记录原始输入或令牌，不启动 AI、不发送消息、不执行真实库存事务。场景响应预先固定，不根据任意订货文本重现业务规则；验证业务规则仍使用现有 DemoService 测试和后续真实后端联调。它不是生产后端。

## 4. 真实后端就绪后的验收顺序

1. **seed + Bearer + /me**：确认真实身份、租户和 allowed_actions，不使用 fixture 标识。
2. **customers + parse**：确认脱敏、候选、库存、字段证据、AI / 兜底与澄清草稿。
3. **save**：验证版本变化、缺货重算、目标行、改价原因和 422 等错误；确认金额仅由后端核算。
4. **approve / decide**：验证 200/202、老板自批、待批锁定、重复批准恢复及并发库存复核。
5. **DO / audit / warehouse**：核对最终单据、差异值、持久化结果和真正的后端字段裁剪。
6. **真实 AI 与部署**：验证冷启动、限流、兜底、公开原型访问和运行证据。

这些属于未完成的真实联调验收。G04～G08 的同日订单、模拟入站、别名管理、演示重置及补充接口仍按契约依赖推进，G10 的 P2 项保持后置。
